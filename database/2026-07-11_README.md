## Apply order

Apply in this order — each is idempotent (re-runnable), but the
intake_periods migration has a seed block that depends on nothing.

1. `2026-07-11_intake_periods.sql` — creates the `intake_periods`
   table + RLS + seeds the current 4-year window. Independent.
2. `2026-07-11_partner_soft_delete.sql` — adds `archived_at` +
   `archived_by_user_id` columns to `partner_students` and
   `partner_applications`. Independent.
3. `2026-07-11_partner_student_notes.sql` — creates the
   `partner_student_notes` table + RLS. Independent.

You can apply all three in a single SQL-editor run if you want —
they don't depend on each other. The order above is just the
recommended sequence for a careful one-by-one deploy.

## Verification queries (run after each migration)

```sql
-- 1. intake_periods
SELECT slug, label, is_active, application_deadline
  FROM intake_periods
 ORDER BY application_deadline ASC NULLS LAST;
-- expect: 8 rows (4 falls + 4 springs) starting with the current year

-- 2. partner_soft_delete
SELECT column_name, data_type, is_nullable
  FROM information_schema.columns
 WHERE table_schema = 'public'
   AND table_name IN ('partner_students', 'partner_applications')
   AND column_name IN ('archived_at', 'archived_by_user_id');
-- expect: 4 rows (2 columns x 2 tables)

SELECT indexname FROM pg_indexes
 WHERE schemaname = 'public'
   AND tablename IN ('partner_students', 'partner_applications')
   AND indexname LIKE '%archived%' OR indexname LIKE '%active';
-- expect: 4 partial indexes

-- 3. partner_student_notes
SELECT column_name, data_type, character_maximum_length
  FROM information_schema.columns
 WHERE table_schema = 'public'
   AND table_name = 'partner_student_notes';
-- expect: id (uuid), partner_student_id (uuid), partner_id (uuid),
--         author_user_id (uuid, nullable), body (text, max 4000),
--         pinned (bool), created_at (timestamptz), updated_at (timestamptz)

SELECT COUNT(*) FROM pg_policies
 WHERE schemaname = 'public' AND tablename = 'partner_student_notes';
-- expect: 5 policies (4 partner team + 1 admin read)
```

## Rollback

Each migration is additive — no existing data is changed. To
roll back: drop the new columns / table (the partners soft-delete
migration drops columns; the notes + intakes migrations drop
the whole table).

```sql
-- Rollback 1
ALTER TABLE partner_students DROP COLUMN IF EXISTS archived_at;
ALTER TABLE partner_students DROP COLUMN IF EXISTS archived_by_user_id;
ALTER TABLE partner_applications DROP COLUMN IF EXISTS archived_at;
ALTER TABLE partner_applications DROP COLUMN IF EXISTS archived_by_user_id;

-- Rollback 2
DROP TABLE IF EXISTS partner_student_notes;

-- Rollback 3
DROP TABLE IF EXISTS intake_periods;
```

Note: the post-deploy code commit may leave the application
broken if rolled back without also rolling back the code. Plan
the deploy order so code lands AFTER migrations.
